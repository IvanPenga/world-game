# Notes for agents working on this project

Read [README.md](README.md) first: it describes the features, the file formats and the project structure. This file
covers conventions and pitfalls that are not obvious from the code.

## Ground rules

- **No git.** This project is not a git repository. Do not run `git init` or commit anything.
- Before finishing, run all four checks and make sure they pass:
  `npx vitest run`, `npm run lint`, `npx tsc -b` and `npx prettier --check src vite-plugins vite.config.ts`.
- Keep [README.md](README.md) up to date when you add or change a feature: the usage sections, "Project structure",
  "What has been done so far", "Roadmap" and "Known limitations".

## Code style

- Prettier: 4 spaces, single quotes (JSX too), no trailing commas, width 120. ESLint runs Prettier as a rule.
- Write names out in full (`properties`, not `props`; `event`, not `e`). Put a JSDoc comment on exported functions and
  types when the name alone does not say what they do. Leave a blank line before `return` after a block of statements.
- Tests live next to the code as `*.test.ts`. Pure logic (`src/world-map`, `src/game`, `src/rendering`, the store)
  gets unit tests; React components have none, so check UI changes in a browser (see below).

## Architecture rules

- `src/world-map/`, `src/game/` and `src/rendering/` must not import React or anything from `src/editor/` or
  `src/components/`. The game will reuse them outside the editor.
- All editor state lives in the zustand store ([editor-store.ts](src/editor/editor-store.ts)). Add behaviour as a store
  action with a store test. Map edits go through `editMap` / `replaceMap` so they are undoable. History entries are
  `{ map, tileset }` snapshots, and "unsaved" is a reference comparison (`map !== savedMap`), so never mutate a map in
  place outside immer.
- [editor.ts](src/editor/editor.ts) creates the app-wide store with a **top-level await** (it lists the files first).
  Tests must not import it. Use `createEditorStore({ map, tileset, repository, drafts })` with an in-memory repository
  and `createMemoryDraftStorage()`, as [editor-store.test.ts](src/editor/editor-store.test.ts) does.
- The editor reads and writes files only through `EditorRepository` ([repository.ts](src/editor/repository.ts)): the
  dev-server API in development and bundled files in production. `bundled-files.ts` (with `import.meta.glob`) is only
  loaded dynamically in production. Importing it statically would make every saved or added map file hot-reload the
  editor and reset its state.
- Lint rules that bite: component files may only export components (react-refresh), so hooks go in
  `src/editor/use-*.ts`. React hooks v7 forbids reading or writing refs during render; use effects or state
  initializers.

## Files on disk

- **Never run Prettier on `src/assets/`** (it is in `.prettierignore`). Map and tileset files use a custom layout (one
  row of tiles or one tile per line), written by [map-file.ts](src/world-map/map-file.ts). A test checks that the
  bundled files round-trip byte for byte, so a reformatted file fails `map-file.test.ts`.
- The dev-server plugin [editor-files-plugin.ts](vite-plugins/editor-files-plugin.ts) runs in Node and imports
  `map-file.ts`, `world-map.ts` and `tileset.ts` from `src/`. Keep those three files free of browser-only code. Imports
  on the Node side use `.ts` extensions, which Vite's upcoming native config loader needs. `map-file.ts` does the same
  for its own imports.
- The plugin skips hot reload for files it wrote itself (it compares the content), so saving keeps editor state.
  Files edited by hand still reload normally.
- Tile ids are positions in the tileset image, and maps store tile ids. **Only add tiles at the end**; never reorder
  or remove them. The art is generated by [tools/generate-art.py](tools/generate-art.py), which also rewrites
  `overworld.json` and `characters.json`. Keep tile names and collision in the script in sync with the JSON.

## Checklists

**New script action**: add it to the `ScriptAction` type and `scriptActionSchema` ([world-map.ts](src/world-map/world-map.ts)).
Then:

- handle it in `runScript` ([game-state.ts](src/game/game-state.ts)) with a test
- add it to `actionTypes`, `actionLabels`, `createAction` and `ActionFields` ([script-editor.tsx](src/components/script-editor.tsx))
- add lint checks if it can be wrong ([lint.ts](src/world-map/lint.ts); `forEachAction` already walks nested actions)
- update the README

**New entity type**: add it to `entitySchema` and `entityTypes`. Then:

- `createEntity` ([entities.ts](src/world-map/entities.ts)) and the `it.each` list in `entities.test.ts`
- `entityStyles` ([map-renderer.ts](src/rendering/map-renderer.ts)), plus a draw function if it has its own look
  (`drawItem` and `drawShip` are pixel grids drawn with `fillRect`, so the recording context in tests can check them)
- the entity form ([entity-panel.tsx](src/components/entity-panel.tsx))
- interaction in the game (`interact` / `arrive` in game-state.ts)
- blocking rules: `isBlockingEntity` in collision.ts (static, used by the editor and lint) and `isEntityInTheWay`
  in game-state.ts (runtime positions of NPCs and ships, picked-up items). Walking, NPC wandering and sailing all go
  through `isEntityInTheWay`
- if it moves at runtime, keep its position in `GameState` (like `state.npcs` and `state.ships`) and never in the map
  entity; add `get<Type>State` / `get<Type>Position` helpers and use them everywhere
- drawing in both game views if it is visible while playing ([playtest-view.tsx](src/components/playtest-view.tsx)
  and [standalone-game.tsx](src/standalone-game.tsx))
- lint checks and the README

**New game mechanic** (like the inventory or sailing): keep all rules in `game-state.ts` as pure functions over
`GameState` and cover them with tests there; views only read state and feed `GameInput`. New state goes into
`createGameState`. Things the side panel or overlays show go into the view's `Hud` type and `getHud` (it compares
fields by reference, so keep immer's structural sharing). If the mechanic changes where the player can go, update
reachability in `lint.ts` too (sailing added ship-reachable coasts there).

## Game runtime pitfalls

- `GameInput.direction` is the key **held** in the current frame. A key pressed and released between two frames is
  never seen, so edge-triggered UI (menu selection) uses `pressedDirection`, and browser tests must hold keys for
  ~200 ms (`keyboard.down`, wait, `keyboard.up`) instead of `keyboard.press` to turn or walk.
- In tests, the `run` helper finishes the step in progress before taking the next one, so a run right after
  boarding or going ashore spends its time finishing that step. Advance with `updateGame(state, world, idle,
  stepDuration)` first.
- The interact key is overloaded: pick up / talk / read / board when walking, and go ashore or interact when
  sailing. The order is in `interact()`; keep it deterministic and tested.
- Item and ship pixel art lives in `map-renderer.ts`, not in `tools/generate-art.py`. The player is drawn between
  the ship and its hull (`drawShip(..., hullOnly = true)`) so they sit inside it.

## Checking the UI in a browser

Playwright is not a project dependency. To drive the app:

1. Install Playwright in a scratch directory (`npm i playwright`).
2. Start `npx vite --port <port> --strictPort`.
3. Launch Chromium with `executablePath` pointing at a cached browser under `~/.cache/ms-playwright/chromium-*/`. The
   newest Playwright may expect a build that is not downloaded yet.

Saving through the UI writes to `src/assets/` for real, so back the folder up first and restore it afterwards. The
user also edits maps in the editor between sessions, so compare files before assuming a change is yours, and never
revert map edits you did not make. Start a playtest on a specific tile by setting
`localStorage['world-editor:last-map']` to the map id, reloading, moving the mouse over the tile (twice, so the
hover registers) and pressing `P`. Read on-screen dialogue with `innerText` on the canvas's parent element, using a
short timeout. Don't
stop servers with `pkill -f <pattern>`: the pattern also matches the shell running the command. Use
`fuser -k <port>/tcp` instead.
